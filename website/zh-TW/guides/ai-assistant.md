# 內建 AI 助手

右下角面板裡的助手是一個帶工具的模型。每一句話都走同一條路：`POST /api/v1/ai/assistant/chat`。前面沒有任何意圖分類器，瀏覽器端與伺服器端都沒有。

模型拿到的是登入者開得了的頁面、眼前這一頁的完整說明，以及這一頁的即時狀態。別頁的說明要用時再讀，回答下方要附的東西用工具表達。回答的文字由模型寫，所有可以點的東西都由伺服器組出來。

## 一輪對話

1. **情境。** `app/ai/assistant/service.py` 用使用者身分、頁面目錄、流程清單、目前畫面的說明與狀態，以及瀏覽器回報的聚光燈步驟組出系統提示詞。
2. **工具迴圈。** 最多呼叫模型 `assistant.max_rounds` 次。最後一輪不提供工具，所以每一輪對話一定以文字收尾。同一則訊息已經寫好回答、工具只是附上按鈕或卡片時，迴圈就此結束，不再請模型多講一次。
3. **檢查。** 回答寫完後檢查一次（見[回答檢查](#回答檢查)）。
4. **回應。** 文字加上工具收集到的附加物。

模型寫回答的同時，文字就一段一段送到瀏覽器（見[逐段顯示](#逐段顯示)）。

| 工具 | 種類 | 做什麼 |
|---|---|---|
| `read_help` | 讀 | 回傳最多三個頁面的完整說明 |
| `get_my_requests` | 讀 | 回傳使用者自己最近的機器申請與進度 |
| `show_pages` | 動作 | 附上最多四顆頁面按鈕 |
| `start_flow` | 動作 | 附上一張多步驟流程卡 |
| `plan_machine` | 動作 | 問齊申請機器的四項需求，再交給規劃器填申請單 |
| `point_at` | 動作 | 在目前頁面上對一個聚光燈步驟打光 |

模型只挑 id。工具的 schema 是逐次請求產生的，enum 裡只有這個使用者看得到的項目，所以按鈕不可能帶到他開不了的頁面。工具執行時會再驗一次 id，不合法就當成錯誤交回給模型。

助手不會送出、建立或修改任何東西。`plan_machine` 的終點是既有的規劃器（`/ai/template-recommendation/recommend`）把申請單填好，仍然由使用者自己檢查後送出。

## 知識

回答的依據只有手寫的定義：

| 內容 | 位置 |
|---|---|
| 一個畫面一個檔：用途、什麼時候用、功能、欄位、彈出視窗、相關頁面 | `backend/config/assistant/screens/<畫面 id>.yaml` |
| 多個畫面共用的片段 | `backend/config/assistant/shared/<名稱>.yaml` |
| 按鈕可以帶去的頁面與存取層級 | `backend/app/ai/assistant/catalog.py` |
| 多步驟流程 | `backend/app/ai/assistant/flows.py` |

每個頁面與畫面都有存取層級，對應 `App.jsx` 的路由守衛：`all`（任何登入者）、`learner`（學生與管理員——學生的課程頁，老師開啟會被導回首頁）、`staff`（老師與管理員）、`admin`。目錄、工具的 enum 與提示詞裡只會有該身分開得了的項目。

這些檔在啟動時由 `screen_files.py` 讀入並用 Pydantic 驗證。形狀不對、鍵重複，或引用了不存在的片段，後端都會啟動失敗。改檔後要重啟才生效。

兩種避免重抄內容的寫法：

- 檔案最上層寫 `extends: <畫面 id>`：先拿另一個畫面的全部內容，再用這個檔寫的鍵蓋過去。給同一頁的第二個網址用。
- `use: <片段>` 展開共用片段：寫成 `elements` 清單裡的一項，或寫在某個視窗裡把片段的 `fields` 與 `notes` 併進來。

`order` 決定畫面的排列位置（小的在前）。同一個網址配得上兩個路徑樣板時取排在前面的那個，所以順序有意義。

寫作規則，由 `backend/tests/test_ai_assistant_knowledge.py` 把關：

- 不描述版面位置，改用按鈕或欄位的名稱指認。
- 視窗標題、開啟它的按鈕與欄位標籤用介面上的原文；測試會拿它們比對 zh-TW 語系檔。
- `constraints` 必須對得上前端真正的驗證規則。
- 相關頁面必須是目錄裡的路由。

## 模型設定

| 設定 | 位置 | 說明 |
|---|---|---|
| 端點、金鑰、模型 | `.env` 的 `VLLM_BASE_URL`、`VLLM_API_KEY`、`VLLM_MODEL_NAME` | 所有內建 AI 功能共用 |
| 模型契約 | `backend/config/llm-model-profiles.yaml` | 模型名稱一定要有對應的項目 |
| 助手行為 | `backend/config/system-ai.json` 的 `assistant` 區塊 | `thinking`、`max_rounds`、`timeout`、`temperature`、`top_p`、`max_tokens` |

`assistant.thinking`（預設 `medium`）是助手每次呼叫模型要求的推理強度，會覆寫模型設定檔裡的全模型預設。只有開／關的模型把 `low`、`medium`、`high` 都當成開。

模型設定檔裡的 `check_thinking: "none"` 讓回答檢查在關閉推理的狀態下執行。推理會超出檢查的 128 個輸出 token 上限的模型要設這一項。

## 回答檢查

通用的遵循檢查不認識助手的正常行為，實測時擋掉了相當比例的正確回答。所以助手把自己的提示詞（`guard.py`）交給共用的檢查器。它只擋三件事：採用別的角色、實際完成了與 SkyLab 無關的要求、宣稱已經替使用者送出或修改了東西。

| 結果 | 回覆 | `degraded` |
|---|---|---|
| 放行 | 模型的回答與附加物 | `false` |
| 擋下 | 固定的範圍說明，不附任何東西 | `false` |
| 檢查器無法使用 | 固定的「請稍後再試」 | `true` |
| 沒有設定模型或模型失敗 | 目前這一頁的固定說明與相關頁面 | `true` |

降級的回覆會寫進 `ERROR` 日誌（沒有設定模型時是 `WARNING`）。

## 逐段顯示

沒問過的問題第一次要等好幾秒：模型通常先用一輪讀說明，下一輪才寫回答。為了不讓使用者對著沒有動靜的面板乾等，`POST /api/v1/ai/assistant/chat` 以 Server-Sent Events 回應：

| 事件 | 內容 | 意思 |
|---|---|---|
| `status` | `{"tool": …}` | 助手剛用完這個工具，還要再想一輪 |
| `delta` | `{"text": …}` | 模型正在寫的字，接在已顯示的內容後面 |
| `reset` | `{}` | 把已顯示的字清掉 |
| `final` | 完整的回應 | 一定是最後一則，也是唯一算數的 |
| `error` | `{}` | 處理到一半失敗，不會再有 `final` |

文字要寫完才能檢查，所以 `delta` 的字只是暫時的。檢查在最後一輪結束後執行，留在畫面上的是 `final` 帶的內容：模型的回答與附加物，或回答被擋下、檢查不了時的固定文字。瀏覽器一律用 `final` 換掉先前顯示的字，存進對話紀錄的也只有 `final`。這表示被擋下的回答可能先出現一下才被換掉。這裡可以接受，因為提示詞裡沒有機密（只有使用者本來就開得了的頁面），而且檢查的目的是讓助手不離題，不是遮住有害內容。

某一輪寫的字後來確定不是回答時會送 `reset`：模型寫了字之後又呼叫了一個必須回應結果的工具，例如讀說明之前先講一句話。模型寫在內容裡的推理（`<think>…</think>`）不會送出去。

頁面按鈕、流程卡與其他附加物只隨 `final` 送達。

模型呼叫本身用 `VLLMClient.stream_chat_completion` 串流，回傳的形狀與一次回完的呼叫相同、通過同一套檢查；串流沒有走到結束原因就斷掉算失敗，不當成比較短的回答。回答檢查仍然是一次回完的單一呼叫。瀏覽器斷線時，模型呼叫會一併取消。

FastAPI 會加上 `X-Accel-Buffering: no`，並每 15 秒送一則 keep-alive 註解。平台的 nginx 認這個標頭，Gateway 的平台入口本來就關閉代理緩衝，所以不必改任何代理設定。中間若有仍然會緩衝的代理，使用者只是變成一次看到整段回答。

## 前端

- `components/AiFloatingChat/useAssistantChat.js` 每一句話都帶著到目前為止的對話、介面語言與畫面情境送出。伺服器不保存對話；瀏覽器依使用者存在 `sessionStorage`，登出時清掉。
- 事件串流由 `services/eventStream.js` 讀取，經 `services/api.js` 的 `apiPostEventStream` 發出（認證與憑證續期跟其他請求一樣；`EventSource` 不能 `POST`，也帶不了 `Authorization` 標頭）。回答還在寫的時候，面板把它顯示成最後一則訊息；這些字放在元件狀態裡，不進保存的對話。還沒有字的時候，「回覆中」的圖示旁邊會寫助手剛做完什麼。
- 頁面要讓助手看到欄位的值與驗證錯誤，就用 `hooks/useAiScreen` 註冊。只有該畫面 YAML 裡宣告過的欄位會進提示詞，標成 `sensitive` 的欄位只剩「有沒有填」。頁面一開始就不該把機密送出來。
- 聚光燈：瀏覽器把目前頁面導覽中 DOM 找得到的步驟送上來，`point_at` 回傳其中一個 id，由 `components/UserGuide/guideCommands.js` 打光。流程步驟對應到哪個既有的 `data-guide` 錨點寫在 `AiFloatingChat/flowAnchors.js`。

## 新增頁面

1. 希望助手能帶使用者過去的頁面，在 `catalog.py` 加路由。
2. 新增 `backend/config/assistant/screens/<id>.yaml`。
3. 照平常的方式加這一頁的聚光燈導覽；助手不必另外設定就能指出它的步驟。
4. 跑 `backend/tests/test_ai_assistant_catalog.py` 與 `test_ai_assistant_knowledge.py`。

## 對真模型檢查

`scripts/AI_live_test/system_ai_guardrails_live.py` 對設定好的模型送出探測案例。助手的案例走正式進入點，用的就是助手的提示詞、工具、推理強度與檢查；查申請的工具拿掉了，探測不會碰到資料庫。不加 `--live` 時只在本機把每個請求組出來檢查一遍。

`scripts/AI_live_test/ai_assistant_live.py` 拿幾個導覽問題實際問助手，每題三輪，檢查回覆附上的頁面按鈕，例如使用者已經在那一頁時，不可以附指向那一頁的按鈕。報告會記下每一次模型呼叫花了多久、第一段文字什麼時候出現。看耗時要看每一題的第一輪：模型閘道可能快取一模一樣的請求，重複的那幾輪會比真正第一次問快很多。

改了提示詞、工具或換模型之後兩支都跑一次。它們的離線測試在 `scripts/AI_live_test/tests/`（`cd backend && uv run pytest ../scripts/AI_live_test/tests`）。
